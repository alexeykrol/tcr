## 1) Что влияет на “автономность” (официальные термины)

В документации Codex автономность определяется двумя слоями:

1) **Sandbox mode** — что Codex *технически может делать* при выполнении команд (где писать, есть ли сеть и т.п.).
2) **Approval policy** — *когда Codex должен остановиться и спросить подтверждение* перед действием.

Ключевая мысль: можно сделать “минимум вопросов”, но при этом всё равно оставаться в ограниченном sandbox.

---

## 2) Важное уточнение про `--full-auto` (чтобы не было сюрпризов)

Согласно CLI reference, флаг `--full-auto` — это удобный алиас, который **ставит**:

> `--ask-for-approval on-request` и `--sandbox workspace-write`

То есть “Auto preset / full-auto” **не** означает `approval_policy = "on-failure"`.

---

## 3) Где и как Codex читает конфиг

Официально:
- Глобальные настройки: `~/.codex/config.toml`
- Проектные оверрайды: `.codex/config.toml` внутри репозитория/папки
- По соображениям безопасности проектные конфиги применяются **только когда проект помечен как trusted** (это поведение описано в Config basics / Security).

Также важен приоритет (упрощенно):
1) CLI flags / `--config` overrides
2) `--profile <name>` (если используешь профили)
3) корневые значения в `config.toml`
4) дефолты

## 4) Практические пресеты (без привязки к конкретной среде)

### 4.1 “Авто, но безопасно” (типичный локальный режим)
Поведение: Codex может читать/править файлы и запускать команды **в workspace**, но будет спрашивать, если нужно выйти за пределы workspace или включить сеть.

CLI (из Security):
```bash
codex --sandbox workspace-write --ask-for-approval on-request
```

Эквивалент:
```bash
codex --full-auto
```

### 4.2 “Редактируй, но спрашивай перед подозрительными командами”
Поведение: редактирование файлов разрешено, но перед запуском “не доверенных” команд будут подтверждения.

```toml
approval_policy = "untrusted"
sandbox_mode = "workspace-write"
```

### 4.3 “Полный YOLO”
Официально это режим без sandbox/approval и **не рекомендуется** (CLI reference / Security):
- `--dangerously-bypass-approvals-and-sandbox` (алиас `--yolo`)
- или `sandbox_mode = "danger-full-access"` (в конфиге)

## 5) Базовые ключи `config.toml` (что чаще всего реально настраивают)

Ниже — “базовые” ключи и таблицы, которые напрямую управляют автономностью, безопасностью, поиском по вебу и тем, что видят команды в shell.
Полный список всех возможных ключей см. в Config reference и/или JSON schema.

### 5.1 Модель и провайдер

```toml
model = "gpt-5.2"          # пример из Config basics
model_provider = "openai"  # провайдер по умолчанию (см. Config reference)
```

Дополнительно (из Config reference):
- `model_instructions_file` — путь к файлу, который заменяет встроенные инструкции (альтернатива AGENTS.md).
- `review_model` — отдельная модель для `/review` (если нужно).

### 5.2 Approval policy (когда спрашивать)

Ключ (Config reference):
```toml
approval_policy = "on-request"
```

Допустимые значения (Config reference):
- `untrusted`
- `on-failure`
- `on-request`
- `never`

### 5.3 Sandbox mode (что “разрешено” технически)

Ключ (Config basics / Config reference):
```toml
sandbox_mode = "workspace-write"
```

Допустимые значения (Config reference):
- `read-only`
- `workspace-write`
- `danger-full-access`

#### Настройки для `workspace-write`

Таблица (Security / Advanced config / Config reference):
```toml
[sandbox_workspace_write]
network_access = false
writable_roots = []
exclude_tmpdir_env_var = false
exclude_slash_tmp = false
```

Пояснения (коротко):
- `network_access`: включает/выключает **исходящую** сеть для команд, которые запускает Codex в sandbox.
- `writable_roots`: дополнительные директории, куда можно писать (помимо workspace).
- `exclude_tmpdir_env_var` / `exclude_slash_tmp`: можно ограничивать доступ к временным директориям.

### 5.4 Web search tool (это отдельное от “сети для команд”)

Ключ (Security / Config basics / Config reference):
```toml
web_search = "cached"   # default
# web_search = "live"   # как --search
# web_search = "disabled"
```

Важно: `web_search` управляет инструментом веб‑поиска в Codex и **не равен** `network_access` (который управляет сетью для shell-команд внутри sandbox).

### 5.5 Переменные окружения для shell-команд

Таблица (Config basics / Config reference):
```toml
[shell_environment_policy]
include_only = ["PATH", "HOME"]
# inherit = "core" | "all" | "none"
# exclude = ["*SECRET*", "*TOKEN*"]
# set = { FOO = "bar" }
```

Это помогает избежать утечек секретов в запускаемые команды и сделать окружение стабильнее.

### 5.6 Профили (удобные пресеты)

Пример (Security):
```toml
[profiles.full_auto]
approval_policy = "on-request"
sandbox_mode = "workspace-write"

[profiles.readonly_quiet]
approval_policy = "never"
sandbox_mode = "read-only"
```

Запуск профиля:
```bash
codex --profile full_auto
```

## 6) Полезные диагностические команды (официальные)

Из Security: можно тестировать sandbox локально:

```bash
# macOS
codex sandbox macos [--full-auto] [--log-denials] [COMMAND]...

# Linux
codex sandbox linux [--full-auto] [COMMAND]...
```

Также упоминается, что `sandbox` доступен как `codex debug`.

## 7) Если нужно “меньше вопросов, но без риска сломать процесс”

Рекомендуемая тактика (особенно когда параллельно работает IDE extension и пишет файлы):

1) Сначала ставь консервативно:
   - `sandbox_mode = "workspace-write"`
   - `approval_policy = "on-request"` (это же поведение `--full-auto`)
2) И только если реально мешает — экспериментируй с:
   - `approval_policy = "untrusted"` (меньше “лишних” подтверждений)
   - `approval_policy = "on-failure"` (может быть удобнее, но это другой режим, не пресет full-auto)
3) Не включай `danger-full-access`/`--yolo` пока не убедишься, что процесс защищен внешне.
